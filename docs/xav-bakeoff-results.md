## The headline finding: psy-tuned vs metric-tuned

xav's output is reproducibly **~9 dB below** a mainline-SVT encode in PSNR **at 24x the
bitrate**:

| Encode | Video bytes | PSNR (frames 1500-1600, Jurassic) |
|---|---|---|
| our xav CRF 6 (Vulkan build, VM) | 647,992,306 | 35.788 dB |
| HomeTower xav CRF 6-8 (CUDA build, host) | 456,898,184 | 35.775 dB |
| ab-av1 CRF 30 (mainline SVT, our flags) | 27,362,327 | **44.498 dB** |

Two machines, two builds, two GPU backends — agreeing to 0.013 dB. Alignment was verified
exhaustively first (crop offset peaks at y=60; temporal offset peaks at 0; levels exactly x4,
source YMIN 23 in 8-bit = 92 in 10-bit; frame counts and rates match).

**Cause:** xav is built on a psy fork with psychovisual features on. Its own guide calls
PSNR/SSIM/**VMAF** *"ancient metrics"* and says `-P|--alt-param` exists partly to *"disable
some psychovisual features that affect metrics badly (such as film-grain, ac-bias, psy-rd)"*
for probing.

**Consequence: VMAF cannot fairly judge xav.** It is not "two metrics, roughly comparable" —
ours actively penalises their tuning. Comparing a psy-tuned and a metric-tuned encode both on
VMAF measures tuning philosophy, not encoder quality. Hence both metrics on both encoders.

### The fork was our choice, not upstream's

`build.sh` has **no default fork**: `SVT_FORK_NAMES=("hdr" "essential" "mainline")`, and with
no fork argument it prompts interactively. We passed `hdr` (originally reasoned from list
order — an inference presented too confidently at the time).

That said, xav is *designed* around psy forks regardless: its hardcoded
`EbSvtAv1EncConfiguration` carries `ac_bias`, `adaptive_film_grain`, `variance_boost_curve`,
`sharpness` — fields absent from mainline. So mainline may not even work (untested).

## Integration constraints (all confirmed, all mandatory)

1. **PTY required.** `src/y4m.rs`: `is_pipe() == !stdin().is_terminal()`, i.e. `!isatty(0)`,
   with **no flag or env override**. Without a TTY xav assumes piped Y4M input, reads nothing,
   writes an ~870-byte file, prints `DONE 100.00%` and **exits 0**. `/dev/null` and closed
   stdin fail identically. Use `script -qec "<cmd>" /dev/null`.
   **Tdarr spawns via Node `child_process` with no TTY — a naive plugin would silently produce
   empty files in production.** (Upstream fix would be one line: `S_ISFIFO(fstat(0))`.)
2. **io_uring must be permitted.** Docker's default seccomp blocks it: the encode succeeds and
   the **mux** fails with `io_uring_setup failed (errno 1)`. Needs `seccomp=unconfined` or a
   profile allowing `io_uring_setup`/`_enter`/`_register`.
3. **Source directory must be writable** — xav writes its hashed temp dir next to the input
   (`os error 30`/EROFS otherwise).
4. **Validate output before reporting success** — non-zero dimensions, frame count within
   tolerance, duration match, size floor. Throw so Tdarr's handler runs and the original is
   never discarded. Emil explicitly wants this gate.
5. **Audio is out of scope** — `sanitizeFile` owns audio in the Tdarr flow; xav runs
   video-only. (Its Opus was 12.5x smaller than DTS, but irrelevant to us.)
6. **TQ restricts preset to 0-7**; 8+ rejected as "real-time usage and inconsistent".
7. **No aomenc.** Encoders: SVT-AV1, AVM, vvenc, x265, x264. Adopting xav means committing to
   SVT-AV1 — Emil has accepted this if SVT delivers.

## Build notes

Builds on Ubuntu in ~6 min, ~22 MB binary. **Not statically linked** despite the README —
needs **GLIBC_2.38**; official Tdarr image is Ubuntu 24.04 / glibc 2.39, so base any build
image on 24.04. FFmpeg version is immaterial (compiles against both n8.1.2 and n9.1-dev;
223 vs 227 fps is noise) — our stack's FFmpeg 8 pin does not transfer to xav.

**One local patch required:** `build_dav1d()` rewrites dav1d's pkg-config `libdir` with a sed
that only strips a bare `lib`/`lib64`. Debian/Ubuntu meson writes
`libdir=${prefix}/lib/x86_64-linux-gnu`, so the multiarch suffix survives into a nonexistent
path and FFmpeg's configure fails with the misleading `dav1d >= 1.0.0 not found using
pkg-config` (pkg-config resolves it; the *link test* fails).

Traps that cost real time:

- **Interrupted build = poisoned artifact.** `cleanup_existing()` judges completeness purely
  by artifact existence. A build interrupted between SVT's PGO *generate* and *use* leaves an
  instrumented `libSvtAv1Enc.a` that looks finished; later builds link it and fail with
  `undefined symbol: __llvm_profile_instrument_target`. Wipe the component dir.
- **`cargo clean` after any dependency change.** `build.sh` skips it on the preset path and
  cargo doesn't track `libSvtAv1Enc.a`, so it reports "Build complete" in 0 s against the old
  binary. This invalidated one of our own test results.
- **AVX-512 effectively required** — 15 hard `target_feature = "avx512bw"` gates, no fallback;
  won't compile at `-C target-cpu=x86-64-v3`.
- **Test suite** needs `git submodule update --init` for `test_files`. With it: 32 pass, and
  all 68 failures are `hw_*`/`dim_hw_*`/`tq::*`, i.e. GPU-dependent — expected on a GPU-less
  box.
- xav's own dep installer knows only pacman/dnf/emerge/brew — **on Ubuntu it silently
  installs nothing**.

## Measurement methodology (learned the hard way)

- **Score every output on the common content region.** xav autocrops (Jurassic
  1920x1080 -> 1920x960; Avatar `crop=1920:1040:0:20`) while our stack encodes the full frame
  including mattes. Cropping only the *reference* leaves baselines scored **with** black bars,
  which encode near-perfectly and inflate their score for free — that is how ab-av1's 27 MB
  appeared to beat xav's 456 MB. Crop both sides.
  On Avatar the mattes are 20px vs Jurassic's 60px, so xav's free pixel-count advantage
  largely disappears — a fairer source.
- **Verify alignment before believing any score**: sweep crop offset and temporal offset and
  take the PSNR peak. A misaligned comparison produces bitrate-independent scores, which is
  the tell.
- **Grainy sources saturate fidelity metrics.** The Jurassic sample (1993 35mm) plateaus
  around 40 dB PSNR regardless of bitrate. This is why HomeTower needed 456.9 MB of AV1 to hit
  SSIMULACRA2 90 on it. Use clean modern sources.
- **Compare video-stream bytes only** — the pipelines emit different audio (av1an's `.vpy`
  carries none, ab-av1 copies DTS, xav encodes Opus).
- **`-v error` suppresses libvmaf's score line** (it is info-level).
- **SSIMULACRA2 scale**: 90+ visually lossless, 70-90 high, 50-70 medium. `-t` is the
  **target score**, not a metric selector — the metric is chosen by which band the number
  falls in. Targeting `10.0-10.2` asks for atrocious quality and pins every chunk at the CRF
  ceiling: a fixed-CRF encode wearing a target-quality costume. **Always check whether the
  CRF range bound.**

## Baselines so far (Jurassic 120 s excerpt, VM — superseded by the Avatar run)

| Config | Time | Video bytes |
|---|---|---|
| av1an + SVT-AV1 p4, target VMAF 95 (per-chunk) | 134 s | 125,904,207 |
| ab-av1 auto-encode + SVT p4, min-VMAF 95 | 39 s | 27,362,327 |
| xav TQ SSIMU2 85 (`-f 10-40`, host) | 126 s | 191,543,588 |
| xav TQ SSIMU2 90 (`-f 1-40`, host) | 142 s | 456,898,184 |

Wall-clock across VM and host is **not** comparable — which is exactly what the Avatar run on
one machine fixes. ab-av1 is a deliberate compromise for low-tier content; **av1an target mode
is the real bar**.
